# 경력 그래프: 이력서 가져오기 · 그래프에 묻기 · 리랭킹

그래프 화면 오른쪽 패널은 두 탭입니다.

- **그래프 만들기**: 경험을 대화로 이야기하거나 이력서·포트폴리오를 올리면 AI가 변경안을 만들고, 사용자가 확인한 것만 적용합니다.
- **그래프에 묻기**: 내 그래프만 근거로 답하고, 문장마다 `[n]` 출처를 답니다. 각 출처에는 노드 id, 라벨, 이름, 본인에서 그 노드까지의 경로가 함께 붙습니다.

스키마 변경은 없습니다. `chat_threads.kind`에 `graph-qa`를 더했고, 문서 텍스트와 답변 출처는 `chat_messages.data`(Json)에 들어갑니다.

## 1. 그래프에 묻기 파이프라인

```
질문 (+ 직전 질문 ×0.3)
  │
  ▼
analyzeQuery ── 토큰(조사 제거) · 한글 바이그램 · 기술 별칭(canonicalSkill) · 소재 태그 · 의도 · 연도
  │
  ▼
① 후보 생성 ── BM25F 어휘 점수 / 기술 일치 / 태그 일치 / 의도 라벨 시드(라벨당 상위 20)
  │            시드가 없거나 overview 질문이면 라벨별 층화 폴백
  ▼
② 그래프 확장 ── 1홉 ×0.5, 2홉 ×0.25 (HAS_SKILL·RELATED_TO는 ×0.5 더), 본인 노드는 거치지 않음
  │              성과 질문: 시드의 ACHIEVED 자식 ×0.8 · 풀 상한 POOL_MAX=60
  ▼
③ 결정적 다중 신호 점수 → 컷오프(0.08, 최소 3개) → MMR(λ=0.8, 앵커당 최대 3개)
  │
  ├─ (후보 > K, 그리고 API 엔진이거나 GRAPH_QA_LLM_RERANK=on, 그리고 남은 시간 > 120초)
  │     ▼
  │   ④ LLM 리랭크: 상위 20개에 관련도 0~3 → 0.6·rel/3 + 0.4·det → MMR 다시
  │      실패·시간 초과(25초)면 ③ 순서 그대로
  ▼
⑤ 상위 K개(기본 8, overview 12, 최소 3)를 번호 붙인 출처 표로 만듦(7,000자 예산) + 그래프 개요
  ▼
⑥ 답변 LLM(task graph-qa, effort low): 문장마다 [n], 자료에 없으면 insufficient
  ▼
⑦ 인용 검증: 없는 번호와 삭제된 노드는 지우고 droppedCitations에 기록, 유효 인용 0개면 grounded=false
  ▼
저장(assistant 메시지, data.kind="graph-answer") → 화면이 폴링
```

그래프는 `getCareerGraph`로 한 번에 읽습니다(사용자당 노드 1000개 이하). 그 뒤 ①~⑤와 ⑦은 모두 메모리 안의 순수 함수이고, Cypher를 새로 쓰지 않습니다.

## 2. 질문 분석 (`analyzeQuery`)

- **토큰.** NFKC로 정규화하고 소문자로 바꾼 뒤 문자·숫자가 아닌 글자에서 자릅니다. 한글 토큰은 끝의 조사·어미를 가장 긴 것 하나만 뗍니다(에서는, 으로, 은/는/이/가, 했던 …). 떼고 남은 어간이 2글자 이상일 때만 뗍니다. 그래서 "성과"는 "성"이 되지 않습니다. 불용어(뭐, 어떤, 알려줘, 경험 …)는 뺍니다.
- **바이그램.** 3글자 이상 한글 토큰은 글자 바이그램을 가중치 0.5로 따로 만듭니다. 형태소 분석기 없이도 "결제개선"과 "결제 개선"이 맞습니다. 문서 쪽은 2글자 토큰은 그대로 쓰고, 3글자 이상은 바이그램으로 나눕니다.
- **접두 일치.** 질문 용어가 2글자 이상 한글이면, 그 용어로 시작하는 문서 토큰도 tf 0.8로 셉니다. 예: "개선"과 "개선했다".
- **기술.** `extractKeywords(q)`와 토큰별 `canonicalSkill`의 합집합입니다. 정식 이름("React")도 용어로 넣어서, 프로젝트 설명에 적힌 "React"와 어휘로 맞습니다.
- **태그.** 토큰을 `resolveStoryTag`로 정확히 맞추거나, 3글자 이상 별칭이 부분 문자열로 들어 있거나, 카테고리 이름이 들어 있을 때 태그로 봅니다. "개선"은 성과 질문에 훨씬 자주 나와서 태그로 보지 않습니다.
- **의도.** 단서 사전으로 정하고, 여러 개가 함께 나올 수 있습니다(achievement, skill, leadership, collaboration, problem-solving, challenge-failure, learning, career, education, certification, project, overview). 대상이 분명한 의도(achievement, skill, education, certification)가 있으면 project 의도는 지웁니다. "결제 개선 프로젝트 **성과**"에서 프로젝트는 주어일 뿐, 묻는 대상은 성과입니다.
- **지시어.** 직전 사용자 질문의 용어를 가중치 0.3으로 섞습니다. "그 프로젝트 성과는?"을 처리하기 위해서입니다. 의도는 이번 질문에서만 읽습니다.

## 3. 신호와 가중치

필드 가중치(BM25F, k1=1.2, b=0.75, 필드 길이는 필드 묶음별 평균으로 정규화)는 다음과 같습니다.

| 필드 | 가중치 |
|---|---|
| 대표 이름(`NODE_TITLE_KEY`), 성과 summary | 3.0 |
| value, metric, myRole, department | 2.0 |
| result, action | 1.5 |
| situation, learned, summary, description, industry, kind, organization, major, degree | 1.0 |
| context: 성과를 이룬 곳(ACHIEVED 출발 노드)의 이름 | 1.0 |
| 기타 문자열(location, issuer …) | 0.5 |

categories는 텍스트로 넣지 않고 tag 신호로만 씁니다. 날짜, 숫자, URL은 색인하지 않습니다.

결정적 점수는 모든 신호를 [0,1]로 맞춘 뒤 가중합을 냅니다(합 1).

| 신호 | 계산 | 가중치 |
|---|---|---|
| lexical | BM25F ÷ 풀 최댓값 | 0.35 |
| skill | 일치하는 Skill 노드면 1, 그 기술을 USED_SKILL로 쓴 노드면 0.7 | 0.15 |
| tag | categories가 질문 태그와 겹치면 1 | 0.12 |
| intent | 의도 라벨과 같으면 1. 관련 라벨이면 낮게: 성과 질문의 result 있는 프로젝트·경험 0.5, 기술 질문의 USED_SKILL 출처 0.5, 경력 질문의 프로젝트 0.3. 리더십은 leadership 태그나 myRole에 팀장·리드·PM·회장이 있으면 1 | 0.12 |
| propagated | 그래프 확장으로 전파된 값 | 0.08 |
| metric | 수치가 있으면(`hasMetric`, 날짜는 제외). 성과 질문이면 성과 노드 1, 그 밖의 노드 0.5. 성과 질문이 아니면 0.3 | 0.08 |
| recency | current이면 1, 그 밖에는 exp(−나이년/4), 날짜가 없으면 0.3. 질문에 연도가 있으면 기간이 겹칠 때 1, 겹치지 않으면 0.05 | 0.04 |
| centrality | log(1+차수) ÷ log(1+최대 차수) | 0.03 |
| completeness | STAR 필드(situation, action, result, learned, myRole)를 채운 비율. 프로젝트·경험만 | 0.03 |

**MMR.** 유사도는 `0.6·[같은 앵커] + 0.4·Jaccard(토큰)`입니다. 앵커는 본인 경로에서 가장 가까운 프로젝트·경험이고, 없으면 직무, 그것도 없으면 노드 자신입니다. 질문 의도와 라벨이 맞는 후보(intent 1)는 앵커 항을 절반으로 줄입니다. "결제 개선 성과" 질문에서 그 프로젝트의 성과들이 프로젝트 노드 때문에 밀려나지 않게 하기 위해서입니다.

같은 앵커에서는 최대 3개까지 뽑고, 성과 질문의 성과 노드는 1개 더 허용합니다. 한도에 걸린 후보는 버리지 않고 맨 뒤로 보냅니다. 동점은 점수, 다음으로 id 순으로 정해서 결과가 매번 같습니다.

λ는 설계 초안의 0.75에서 0.8로 올렸습니다. 0.75에서는 "결제 개선 프로젝트 성과가 뭐였어?"의 프로젝트 노드가 상위 3 밖으로 밀렸습니다(골든 셋 기준).

**개요 질문과 폴백.** overview 의도와 층화 폴백에는 컷오프를 두지 않고 K=12까지 넓게 봅니다.

## 4. LLM 리랭크(선택)

- **실행 조건(모두 만족)**
  - 결정적 후보 수(컷오프 후)가 K보다 많습니다.
  - `GRAPH_QA_LLM_RERANK`가 `off`가 아닙니다.
  - Claude API 엔진입니다. CLI 엔진은 호출 한 번에 수십 초가 걸려서 `GRAPH_QA_LLM_RERANK=on`일 때만 돌립니다.
  - 답변 마감까지 120초 넘게 남았습니다.
- **입력.** 후보 한 줄씩(≤180자)을 `<graph_sources>`로 감싸 보냅니다. 예: `[c3] 성과 · 결제 정산 배치 시간 단축 · 6시간→40분 / 처리 시간 · 경로: 나 → 페이랩(회사) → …`. LLM에는 노드 id 대신 `c1…c20`만 보입니다.
- **출력.** `{ ratings: [{ id, relevance: 0~3 }] }`(평평한 구조)입니다. task는 `graph-qa-rerank`, effort는 `low`, `cacheUser:false`입니다.
- **결합.** 후보 밖 id는 무시합니다. 빠진 후보는 관련도 1로 봅니다. `final = 0.6·rel/3 + 0.4·det`이고, rel이 0이면서 det < 0.5이면 버립니다. 그 뒤 MMR을 다시 돌립니다.
- **실패.** 별도 `AbortSignal.timeout(25s)`를 걸고 부모 마감과 `AbortSignal.any`로 묶습니다. 어떤 예외가 나도 결정적 순서를 그대로 쓰고, `debug.llmRerank = {used:false, reason}`만 남깁니다. 부모 마감이 지난 경우에만 예외를 다시 던지고, 그때는 답변도 실패로 저장됩니다.

## 5. k와 토큰 예산

| 항목 | 값 |
|---|---|
| POOL_MAX(후보 풀) | 60 |
| intent 라벨 시드 | 라벨당 20 |
| LLM 리랭크 입력 M | 20 |
| 답변 컨텍스트 K | 8 (최소 3, overview 12) |
| 컨텍스트 글자 | 7,000자(한국어 약 4~5k 토큰). 출처 하나에 900자 이하, 속성 값은 200 → 120 → 60자로 줄여 가며 맞추고, 그래도 넘으면 낮은 순위부터 뺌 |
| 그래프 개요 | 400자 이하(라벨별 개수와 덜 채운 필수 경험) |
| 이전 대화 | 최근 6개, 2,000자(메시지당 600자) |
| 질문 | 1,000자 |
| 답변 max_tokens | 8,000. 출력 목표는 1,200토큰 안팎이지만, Opus 5.5는 thinking 토큰도 max_tokens에 들어감 |
| 리랭크 max_tokens | 4,000. 출력은 600토큰 안팎 |

## 6. 출처와 경로

- **번호와 노드.** LLM은 node id가 아니라 번호만 냅니다. 번호를 노드에 연결하는 표(`GraphSource[]`)는 서버가 갖고 있어서, LLM이 없는 id를 지어낼 수 없습니다.
- **경로 계산(`personPaths`).** 엣지를 무방향으로 보고 Dijkstra를 돌립니다. 비용은 아래와 같고, 동점이면 앞 노드 id 사전순입니다.

  | 관계 | 비용 |
  |---|---|
  | HAD_ROLE, AT_COMPANY, WORKED_ON, PART_OF, ACHIEVED, HAS_EXPERIENCE, STUDIED_AT, EARNED | 1.0 |
  | WORKED_AT | 1.2 |
  | USED_SKILL | 1.5 |
  | HAS_SKILL | 1.8 |
  | RELATED_TO | 2.0 |

- **회사 끼워 넣기.** 직무 앞에 소속 회사를 넣습니다: `나 → 페이랩(회사) → 백엔드 개발자(직무) → 결제 개선(프로젝트) → 6시간→40분(성과)`. 직무 없이 회사·경험·학력에 PART_OF로 붙은 프로젝트는 그 상위 노드를 앞에 넣습니다.
- **연결 안 된 노드.** 본인과 이어지지 않은 노드는 `[나, 노드]`로 두고 "(나와 연결되지 않음)"을 붙입니다.
- **조회 시 재확인.** 스레드를 조회할 때 그래프를 한 번 읽어 각 출처에 `exists`를 표시합니다. 그래프를 읽지 못하면 표시 없이 내려줍니다. 삭제된 노드의 칩은 흐리게 하고 누를 수 없게 합니다.
- **칩과 그래프 연결.** 출처 칩이나 `[n]`을 누르면 `career-graph:focus` 이벤트가 나갑니다. 그래프 보기는 그 노드를 선택해 상세를 열고, 경로의 노드와 엣지를 강조한 뒤 관계도로 스크롤합니다.

## 7. 실패 모드

| 상황 | 동작 |
|---|---|
| 그래프가 비어 있음 | LLM 없이 즉시 안내하고, 체크리스트 제안 버튼을 띄움 |
| 후보 0개 / 관련 없는 주제 | 층화 폴백을 쓰고, 출처 표 앞에 "직접 맞는 항목 없음" 안내를 붙임. LLM이 `insufficient`를 내면 제안 버튼을 띄움 |
| LLM 리랭크 실패·시간 초과 | 결정적 순서로 진행하고 `debug.llmRerank.reason`에 남김 |
| 답변 LLM 실패 | `status:"failed"`, `data:null`. 다시 시도 버튼(retry 라우트) |
| 서버 재시작으로 답이 오지 않음 | 330초 뒤 stale로 보고 다시 시도를 허용 |
| 무효 인용(없는 번호, 사이에 삭제된 노드) | 마커를 지우고 `droppedCitations`에 기록 |
| 유효 인용 0개 | `grounded=false`, `insufficient=true`로 보정. 화면은 "그래프에서 근거를 찾지 못한 답입니다" 경고 |
| 답변 뒤 노드 삭제 | 조회할 때 `exists=false`. 칩을 흐리게 하고 "삭제된 항목"으로 표시 |
| 동음이의 기술(Go 등) | `canonicalSkill`의 exact 규칙을 따름(이름 전체가 별칭과 같아야 함) |
| 조사 제거 오류 | 바이그램과 접두 일치가 받쳐 줌 |
| 남용 | `GRAPH_QA_LIMIT`(사용자당 10분 30회, DB 원장)를 넘으면 429 |

## 8. 평가 계획

- **고정 그래프.** `__fixtures__/qa-graph.ts`는 회사 2, 직무 2, 프로젝트 4, 경험 2, 성과 5, 기술 8, 학력 1, 자격증 1로 되어 있습니다.
- **골든 셋.** `retrieve.golden.test.ts`에 한국어 질문 12개와 기대 상위 노드를 적어 두었습니다.

| 질문 | 기대 |
|---|---|
| 결제 개선 프로젝트 성과가 뭐였어? | 성과 "결제 정산 배치 시간 단축" 1위, 프로젝트 "결제 개선" 상위 3 |

- **기준선(CI 회귀 방지).** 1위 정확도 ≥ 80%, recall@3 = 100%, MRR ≥ 0.9입니다. 현재는 셋 다 만점입니다.
- **가중치 조정.** 가중치·λ·컷오프를 바꿀 때는 이 테스트를 통과하는 범위에서 바꿉니다. 실패한 질문을 골든 셋에 더하는 식으로 셋을 키웁니다.
- **운영 관찰.** 개발 환경에서는 `debug`(의도, 기술, 태그, 풀 상위 20개의 신호·det·llm·final, LLM 리랭크 사용 여부와 시간, 컨텍스트 글자 수)가 메시지 data에 저장되고 화면의 `<details>`로 보입니다. 운영 응답에서는 뷰가 지웁니다. 서버 로그 `[graph-qa]`에는 인용 수와 무효 인용 수를 남깁니다. 운영 지표로는 칩 클릭률과 무효 인용 비율을 봅니다.

## 9. 이력서·포트폴리오로 그래프 채우기

1. 그래프 만들기 탭에서 [이력서·포트폴리오로 채우기]를 누르면 FileDrop(PDF·DOCX·HWP·HWPX·HTML·TXT·MD), 붙여넣기 칸, 문서 종류 선택이 나옵니다. 열린 대화가 없으면 먼저 대화를 만듭니다.
2. POST `/api/graph/chat/threads/[threadId]/import`(multipart, `maxDuration=300`)가 다음 순서로 처리합니다.
   - 스레드 확인
   - `readFormDataLimited`: 용량 초과면 413
   - `extractText`: 실패하면 `IngestError`(400·413·415)
   - 50자 미만이면 400
   - 20,000자에서 자르고 경고를 남김
   - 사용자 메시지 저장: 대기 중이면 409, `GRAPH_IMPORT_LIMIT`(24시간 10회)를 넘으면 429
   - 202를 돌려주고 `after()`에서 답을 만듦
3. **원본 파일은 저장하지 않습니다.** 사용자 메시지 `data`에는 `{kind:"document-import", docKind, fileName, text, chars, truncated, warnings}`만 남습니다. 화면용 응답에서는 `text`를 비웁니다.
4. 답변 단계(task `graph-import`, `GraphImportOutputSchema`, 연산 ≤150)의 결과는 `proposalFromOutput(..., {maxOps:150, sourceText})`가 다음 순서로 정리합니다.
   - 삭제 연산 거부
   - `verifyAgainstDocument`
     - 회사·학교·자격증: 이름이 문서에 있어야 합니다. 회사는 (주)·주식회사를 뗀 키로 비교합니다.
     - 기술: 사전의 정식 명칭이 문서의 기술 키워드에 있어야 합니다.
     - 직무·프로젝트·경험: 이름 낱말의 60% 이상이 문서에 있어야 합니다.
     - 성과: 숫자가 모두 문서에 있어야 합니다.
     - 빠진 노드를 가리키는 연결은 `validateAgainstGraph`가 연쇄로 걸러 냅니다.
   - 중복 병합: 기술은 `skillKey`("리액트" = "React"), 회사는 접미사를 뗀 이름으로 비교합니다. 이 병합은 대화 경로에도 적용됩니다.
   - 소재 분류 병합과 검증을 거칩니다.
5. 적용은 기존 apply 라우트를 그대로 씁니다. `source:"document-import"`인 변경안만 `applyGraphOps(..., {maxOps:150})`를 쓰고, 직접 편집 API는 60 그대로입니다.
6. 이후 대화에서는 문서 메시지를 본문 대신 한 줄로 넣습니다. 가장 최근 문서는 8,000자까지 `<resume>`/`<portfolio>`로 프롬프트에 함께 넣어서 "아까 이력서의 자격증도 넣어줘"가 됩니다. 다시 시도하면 읽어 낸 글(`data`)까지 다시 보냅니다.
7. 시간 초과는 "문서를 나눠 붙여넣어 주세요"로 안내합니다.

## 남은 결정

- **LLM 리랭크 기본값.** CLI 엔진에서는 기본으로 끄게 했습니다(지연 시간이 두 배가 될 수 있음). 운영에서 API 엔진의 리랭크 효과는 debug 로그로 확인한 뒤 유지 여부를 정합니다.
